How Pixel Coordinates and the Magnifier Work

The point under your cursor, the pixel stored in the file, and the physical dot on the screen are three different things — this guide sorts out the coordinate system, the magnifier and the zoom anchor.

The image coordinate system

The image coordinate system starts at the top-left corner (0,0): x grows to the right, y grows downward — the opposite of the axis-up system from maths class. Picking, depth reading and grid drawing all use this one system.

Coordinates address pixel cells: the point (37, 12) is the cell in column 38, row 13 (rows and columns are counted from 0). Off-by-one here shifts everything by a whole cell when you align against a design or write a slicing script.

Three kinds of pixels

The same "1 pixel" means three different things. On a 2× display (devicePixelRatio = 2) with the image shown at 100%:

NameWhat it isOn a 2× screen
Image pixelSample point stored in the file; coordinate readings use itOne becomes a 2×2 block of device pixels
CSS pixelLayout unit; the basis for devicePixelRatio conversion1 CSS px = 2 device px
Device pixelPhysical light dot on the panel, the smallest unit you actually seeResolution is twice the nominal CSS size

That is why interfaces look "twice as large" on high-DPI screens: the CSS numbers never changed — one CSS pixel simply lands on more physical dots. When reading coordinates, always trust image pixels; screen resolution plays no part.

The magnifier

While you hover, the panel next to the tooltip draws an 11×11 neighbourhood of pixels around the cursor, each cell 16 pixels square. The centre cell carries a white stroke — watch that frame when you pick, so a shaky hand cannot land one cell off.

Inside the magnifier, smoothing is explicitly disabled (imageSmoothingEnabled = false), so cell edges stay crisp instead of being blurred by interpolation. At image boundaries the area outside the picture is not mirrored: the source rectangle is clipped to the image bounds first, and cells with nothing to sample simply show the magnifier's black backing — a black edge means the cursor is against the border of the image.

The pixel grid

The pixel grid appears at 14× zoom and above. Below that ratio the lines collapse into mush and only get in the way; at 14× each cell has enough screen space for the grid lines to sit exactly on pixel boundaries. The mouse wheel zooms from 2% to 6400%, and double-clicking the image fits it to the window.

Zoom anchored to the cursor

When you zoom with the wheel, the anchor stays under the cursor: after zooming in, the cursor still points at the same pixel instead of drifting away. The whole conversion is one line:

view.x = px - (px - view.x) * (ns / view.scale);

Read it as: new offset = cursor − (cursor − old offset) × (new scale ÷ old scale), which keeps the image point under the cursor at the same screen position across the zoom. The y direction uses the identical formula.

What people use it for

  • Slice alignment: confirming a sprite sheet boundary does not swallow a row of pixels;
  • Pixel-art review: checking palette choices cell by cell along with stray pixels;
  • Sprite edges: verifying atlas alignment and padding after export;
  • Design handoff: confirming a 1px border really renders as 1px once the device pixel ratio is converted.

Depth maps are read on exactly the same coordinate system — see the depth map guide. If you only need the colour of one cell, see the colour picker guide.

Why native browser zoom is not reliable

Full-page browser zoom takes a different rendering path: it reflows the layout first, then interpolates the image up, handing you a smoothed approximation. The result also depends on image-rendering, whose browser defaults differ, so the same file can look different when magnified in two browsers. The canvas here only enables interpolation while shrinking (scale < 1); zooming in always samples nearest-neighbour. Going to 14× with the grid on is the dependable way to inspect pixels.
