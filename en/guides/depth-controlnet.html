16-bit Depth Maps in ControlNet

Depth is ControlNet's keep-structure-change-skin channel: it only tells the model what is near and what is far. This guide covers sources, units and what to verify before generating.

What the depth channel shows the model

The depth model receives one greyscale image: brighter is nearer, darker is farther (a few implementations invert this — see the triage table). It injects the spatial skeleton — depth relations, occlusion edges, volume outlines — into sampling, while colour, material and lighting stay with the prompt. That is why depth preserves composition while changing style, where a lineart ControlNet would copy every stroke.

ChannelLocksTypical use
DepthNear-far structure and occlusionRestyle or re-material while keeping staging
Canny / lineartEvery contour lineFaithful redraws, colouring, exact layout copies
NormalSurface orientation and curvatureRelighting reliefs and curved surfaces

Rule of thumb: if the composition lives in object placement, choose depth; if it lives in drawn lines, choose lineart; for both, stack two ControlNets at moderate weights — the guidance budget principles in Prompt Weighting (a:b): Syntax and Tuning apply here too, since over-driven guidance always produces artefacts.

Three sources of material

SourceFormat and precisionWatch out for
Phone / camera captureJPG preview or 16-bit TIFF depthEdge holes — inspect the zero-value share
Renderer Z-depth export16-bit integer or 32-bit float TIFFCleanest data; align the mm/metre convention
Model-generatedPlain 8-bit greyscaleLowest precision, zero cost — fine for drafts

The first two open in the browser at full precision — 16-bit integer TIFF values display as millimetres, 32-bit float TIFF parses as metres with automatic conversion, and 0 counts as invalid depth (sensor hole or uncovered render), shown as transparent. Full details live in the 16-bit TIFF depth map guide.

Two checks before generating

One: range and invalid values. Open the pixel viewer and sample a few points: values should sit in a plausible distance window (say 0.5-8 m), and translucent zeros must not cover the subject. Then open the image histogram in depth mode — the x-axis is millimetres, the main peak is where the subject sits, and zeros are counted separately. Zeros stacked on the subject mean no depth information there: ControlNet will treat that as a structural hole, so patch it or change the source.

Two: normalisation and resolution. Most front-ends end up feeding an 8-bit greyscale map, so 16-bit and float sources must first be normalised so the valid range fills 0-255 — normally the pre-processor's job or an external app's. These tools stop at inspection: they confirm units, range, invalid regions and polarity, then you hand the file to the generator. Pixel-identical resolution is not required, but the crop must match the base image or the structure lands in the wrong place.

Symptom triage

Verification flow in ImageLab

  1. Open the file in the pixel viewer: 16-bit/float values in millimetres, zeros transparent — confirm range and unit point by point;
  2. Switch the histogram to depth mode: read the distance peak and the zero share to judge usability;
  3. For colour cross-checks use the picker and the pixel inspector guide; file-level problems (all black, absurd numbers) go straight to the depth map guide;
  4. Once the source verifies clean, mount the depth ControlNet and climb the weight from low.

FAQ

Must the depth map match the base image size?

The composition must match; exact pixels are not mandatory. Misaligned crops break structure far worse than a resolution difference.

Why is half of it transparent on open?

Pixel value 0 renders as transparent because it counts as invalid depth — sensor holes or uncovered render. Over the subject, patch or replace; at the edges, crop.

Can a depth map double as a black-and-white photo?

No — it encodes distance, not brightness; colouring it directly yields a strange "nearer is whiter" image. Use false colour if you need to visualise it.

Is 16-bit better than 8-bit?

16-bit gradients are smoother and suited to final output; 8-bit is fine for drafts. The real requirement is normalising so the valid range fills 0-255.
